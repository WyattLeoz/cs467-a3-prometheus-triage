## What happened

`PrometheusNotificationQueueRunningFull` in `documentation/prometheus-mixin/alerts.libsonnet` can never fire on a current Prometheus. Its expression compares two series that no longer carry the same labels:

```
predict_linear(prometheus_notifications_queue_length{...}[5m], 60 * 30)
>
min_over_time(prometheus_notifications_queue_capacity{...}[5m])
```

`prometheus_notifications_queue_length` has an `alertmanager` label (one series per Alertmanager URL). `prometheus_notifications_queue_capacity` does not. A binary operator pairs series on their full label set, so the two sides never match and the result is always empty. The rule loads, reports `health="ok"` and `state="inactive"`, and stays that way even with a full queue, so nothing looks wrong.

## Evidence

Prometheus v3.15.0, one Prometheus with one Alertmanager target:

```
prometheus_notifications_queue_length{alertmanager="(10.244.1.91/redacted) instance=..., job=...}   -> 1 series
prometheus_notifications_queue_capacity{instance=..., job=...}                                                      -> 1 series
```

The left side has an extra `alertmanager` label, so 0 pairs match. Observed on the kube-prometheus-stack 88.6.2 copy of the rule, which is generated from this mixin.

## Expected

The alert fires when the notification queue is predicted to fill within 30 minutes.

## Suggested fix

Drop the `alertmanager` label from the left side so both sides have the same labels:

```
(
  max without (alertmanager) (
    predict_linear(prometheus_notifications_queue_length{%(prometheusSelector)s}[5m], 60 * 30)
  )
>
  min_over_time(prometheus_notifications_queue_capacity{%(prometheusSelector)s}[5m])
)
```

`max` takes the fullest queue, which is the one to alert on. `ignoring(alertmanager)` alone is not enough: with more than one Alertmanager it turns the mismatch into many-to-one matching and errors. I run this corrected copy in production; the same fix was made downstream in thaum-xyz/ankhmorpork#1274.
